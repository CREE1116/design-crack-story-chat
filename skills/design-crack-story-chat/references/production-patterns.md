# 제작정보에서 추출한 재현성 높은 패턴

## 사용법

이 문서는 커뮤니티 제작정보를 현재 크랙 프로젝트에 적용할 때의 판별표다. 오래된 플랫폼 내부 관찰은 원리가 아니라 가설로 취급한다. 실제 크랙에서 확인되지 않은 발동 수, 순서, 변수명, 우선순위, 미디어 로딩, 저장 API는 고정 규칙으로 쓰지 않는다.

## 항상 적용할 원칙

### 0. 장면은 도미노다

각 장면을 `목표→충돌→결과/Yes-but→반응→딜레마→결정`으로 압축 점검한다. 결과는 다음 문제를 만들고 결정은 다음 장면 목표를 만든다. 모든 칸을 매번 서술하지 않아도 되지만, 인과 고리가 끊긴 장면은 요약·삭제·재설계한다. 목표(얻으려는 것)와 대가(실패 시 잃는 것)를 분리한다.

### 1. 빈칸도 예산이다

프롬프트가 길수록 지능·정밀도가 자동 상승하지 않는다. 매 턴 결과를 바꾸는 규칙만 통합본에 둔다. 후속 장면의 안정적 설정은 키워드북, 변하는 사실은 대화 맥락, 한 번만 필요한 진입 정보는 시작 프롬프트로 보낸다. 그래도 첫 등장·첫 판정에 필요한 씨앗·능력 불변식·주도권·출력 계약은 항상 남긴다. 키워드북은 동시 3개뿐이므로 장면별 0~2개를 계획하고, 다음 턴에 필요할 상세는 자연스러운 NPC 대사·서술로 키워드를 한 턴 먼저 꺼내 준비한다.

### 2. 규칙은 조건→행동→대체 경로로 쓴다

`누가/언제→무엇을→그럴 수 없으면 무엇을`을 한 줄로 만든다. `능동적으로`, `자연스럽게`, `절대` 같은 우선순위 구호만으로 행동을 기대하지 않는다. 이벤트는 `trigger/block/effect/repeat/stop`을 갖고, 실패·거절·지연도 다음 상태나 사건을 만든다. 이벤트 강제 발동용 마법 토큰이나 전역 override는 쓰지 않는다.

### 3. 숫자는 표현이 아니라 엔진이 관리한다

관계·성격·위험은 `stage + 관찰 가능한 허용 행동 + 마지막 원인`을 주축으로 한다. 숫자가 필요하면 범위·변화 원인·회차 상한·중복 보상 방지·단계 전이를 명시하고 애플리케이션이 검증한다. 모델이 계산해야 하는 합산식은 중간값을 순서대로 보여주거나 앱에서 계산한다. 아이콘은 안정적 ID의 표시일 뿐 의미의 원본이 아니다.

### 4. 성격은 형용사보다 반응 벡터다

공용 아키타입·MBTI·Big Five는 압축용 초기값일 뿐이다. 욕구·공포·모순·평상/불확실/도전/실패/신뢰/경계침해 반응과 금지선을 붙인다. `집착·냉혹·제멋대로` 같은 단어는 범위와 배려 경계를 명시하지 않으면 과잉 해석된다. 관계·선호·대사 표본도 성격을 구성하지만, 예시는 새 정사나 플레이어 행동을 만들지 않는다.

### 5. 다인극은 공간과 상호작용을 모델링한다

각 장면에 중심 인물, 위치·거리·시선·사용 가능한 물건, 참여자별 목표를 둔다. 플레이어가 침묵해도 목표가 있는 NPC끼리는 서로 말하고 행동할 수 있다. 단, 한 응답에 모든 인물이 발언할 필요는 없고 주요 플레이어 결정 전에는 멈춘다. 공간 정보가 없으면 대화가 메신저처럼 분리되는지 테스트한다.

### 6. 예시는 자연어, 상태는 구조화

말투·묘사·출력 모양을 가르칠 때는 실제로 보일 자연어 예시를 1~3개 넣는다. JSON/키값은 실제 앱 파서가 확인된 경우에만 사용한다. JSON이 주의를 강제하거나 보안을 제공한다고 주장하지 않는다. 공개 상태창은 이미 대화에서 확인된 사실의 짧은 요약일 뿐, 비밀·숨은 플래그·추론을 포함하지 않는다.

### 7. OOC와 프롬프트 추출은 별도 라우팅한다

OOC 요청은 `설정 질의/진행 제어/메타 질문/프롬프트·비밀 추출`로 분류한다. 허용된 제어 요청만 짧게 처리하고, 추출·정책 우회·숨은 지시 공개는 거절하거나 인게임 대안으로 전환한다. OOC 허용을 전체 규칙 해제로 오해하지 않는다. OOC 응답이 인게임 상태를 임의로 바꾸지 않게 한다.

### 8. 상태창은 공개 요약이되, 연속성 운반은 별개 문제다

상태창에는 플레이어가 이미 본 사실만 보인다. 숨은 수치 장부나 세이브·로드 명령으로 취급하지 않고, 확인되지 않은 크랙 기능에 기대는 보존·복원 포맷도 만들지 않는다.

다만 **무엇을 담느냐와 얼마나 자주 내보내느냐는 다른 결정**이다. 관계 단계, 장비·소지품, 등급, 날짜·시각을 항상 보여주는 고정 HUD를 약속한 작품이면 매 응답 같은 위치·필드 순서로 출력하고 직전 공개값을 계승한다. 그렇지 않은 단순 요약은 새 공개 정보가 없을 때 생략한다. 어느 쪽도 별도 대화기록·저장 API나 영속성 보장으로 취급하지 않는다.

### 9. 후반 테스트는 상태를 직접 주입한다

성격 전이·반전 공개·위기·엔딩 직전 같은 기능은 프롤로그부터 재생하지 말고, 바로 직전까지의 짧은 대화 발췌를 넣어 테스트한다. 기대값은 특정 문장이 아니라 불변조건(누가 무엇을 알고 있는가, 어떤 단계 행동이 허용되는가, 어떤 선택에서 멈추는가)으로 기록한다. 별도 상태 파일이나 메모리를 만들지 않는다.

## 인물을 자기 역할에 가두지 않는다

배포된 작품들이 공통으로 넣는 두 줄이 있다. 둘 다 "인물이 플레이어의 위성이 되는" 실패를 막는다.

```text
모든 ⓒ는 ⓤ와 무관하게 각자 설정대로 자율 행동한다.
모든 ⓒ는 ⓤ에만 매몰되지 않으며 업무·휴식·동료 관계·사생활을 같은 비중으로 유지한다.
```

여기에 한 줄을 더 붙이면 능력물·직업물에서 특히 효과가 크다.

```text
모든 ⓒ는 자기 직업·등급·전투력에 매몰되지 않고 취향·일상·관계 형성을 같은 비중으로 유지한다.
```

등급 체계가 있는 작품은 인물이 **등급의 화신**이 되기 쉽다. S급은 늘 S급답게만 행동하고, 의무관은 의무 얘기만 한다. 위 줄은 그 붕괴를 직접 막는다.

### 중립성은 양쪽을 다 막는다

```text
ⓒ는 ⓤ를 주인공화·설정 외 특혜·의존·긍정 편향×. 부정 편향하라는 뜻이 아니며, 가능성을 열어 둔다.
```

뒷문장이 없으면 모델이 과보정해서 인물들이 이유 없이 냉담해진다. **금지의 반대쪽도 같이 막아야** 중립이 된다.

## 조건부로만 쓰는 패턴

- 관계 수치 대신 질적 단계: 거의 항상 권장. 숫자·응답 횟수로 자동 연애를 만드는 방식은 관리형 게임에서만 사용.
- 랜덤·주사위: 실패 가능성과 범위를 실제로 정의할 때만. 무작위가 플레이어 선택을 무효화하지 않게 하고, 같은 입력에 매번 다른 결과가 필요하면 시드/앱 권한을 확인.
- 동적 성격 형성: 장기 성장물에서만. `trait stage` 전이는 묘사된 사건과 한정된 변화폭에 연결하고, 모델의 임의 수치 계산에 맡기지 않는다.
- 이미지·미디어에 성격/설정을 싣기: 실제 미디어가 항상 로드되는지 확인한 뒤 보조 정보로만 사용. 핵심 규칙은 텍스트에 둔다.
- 저장/로드 명령어: 실제 UI·파서가 있을 때만 공개 명령으로 만든다.

## 버릴 패턴

- `!!!`, 영문 대문자, 반복된 `최우선`, 처벌·초기화 문구가 의미 경계를 대신한다는 믿음.
- 비밀을 암호화·이름 변경·강한 금지문으로 숨기기.
- 현행 확인값(동시 3개)보다 많은 키워드북을 한 장면에 의존시키거나, UI에서 확인하지 않은 우선순위·지속시간·정규식 문법을 단정.
- 하트·이모지·응답 횟수만으로 관계·동의·시간을 판정.
- JSON을 주의집중·보안·정확성의 마법으로 사용.
- 예시 구분자에 숨은 추가 슬롯을 끼워 넣거나, 플랫폼 미지원 변수·상태 API를 추정.
- 최소 문단 수, 매 턴 질문, 매 턴 사건·호감도·이미지 출력 강제.

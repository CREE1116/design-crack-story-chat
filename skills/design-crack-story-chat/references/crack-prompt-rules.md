## 적용 범위

이 문서는 `story.md`와 `characters.md` 두 원본을 크랙의 **최종 파일 5개**로 조립할 때의 규칙을 소유한다. 시스템 규칙은 별도 원본에 쓰지 않고 빌드 순간 최종 파일에 직접 넣는다. 문장 단위 작성법은 [prompt-writing.md](prompt-writing.md), 파일별 원본 소유권은 [file-architecture.md](file-architecture.md)를 따른다.

크랙이 지원하는 실제 변수명, 글자 수, 이미지 태그, 상태 저장 API가 프로젝트에 명시되어 있으면 그 사양을 우선한다. 확인되지 않은 `{user}`, `{{player}}`, 코드블록 이름, JSON 필드를 임의로 플랫폼 기능이라고 가정하지 않는다. 예시 토큰은 실제 지원 문법으로 치환한다.

## 7000자 제한과 예산

- SAFE/UNSAFE **각 통합 프롬프트는 7,000자 이하**로 유지한다. 시스템 역할, 핵심 인물, 상시 세계관·스토리 엔진, 생성 규칙, 출력 규칙, 선택 프로필 delta를 각 파일 안에서 합산한다.
- 최종 산출물은 `프롤로그·SAFE 통합·UNSAFE 통합·시작 프롬프트·키워드북 등록표` 정확히 5개다.
- 플레이어 프로필, 프롤로그, 시작 상황은 통합 프롬프트 예산에서 제외한다. 플레이어 프로필은 크랙이 외부에서 제시한 양식에 대한 첫 사용자 입력으로 받는다.
- 프롤로그와 시작 프롬프트는 각각 1,000자 이하로 유지한다.
- 원본 Markdown 전체를 7,000자로 제한하지 않는다. 상시 필요한 확정 원본만 선별·압축한 통합 조립본에 한도를 적용한다.
- 최소 분량 목표는 없다. 필요한 규칙을 모두 담은 뒤 가능하면 6,500자 이하에서 멈춰 수정, 변수 치환, 플랫폼별 추가 문구 여유를 남긴다.
- 별도 계산 규칙이 확인되기 전에는 공백, 줄바꿈, Markdown 기호를 포함한다. 검사기는 유니코드 문자 수와 UTF-16 코드 단위를 모두 계산하고 더 큰 값을 보수적으로 적용한다.
- 집필 중에는 두 원본의 사실만 다듬고, 시스템 블록은 별도 초안으로 만들지 않는다. 실제 길이 검사는 완성된 최종 통합본에서만 한다.
- 게시 직전에는 두 통합본을 각각 검사한다: `python scripts/check_prompt_length.py --require-single build/integrated-prompt-safe.md`와 동일한 방식으로 `build/integrated-prompt-unsafe.md`를 검사한다.
- 프롤로그와 시작 프롬프트도 각각 검사한다: `python scripts/check_prompt_length.py --require-single --limit 1000 --target 900 build/prologue.md`와 동일한 방식으로 `build/start-prompt.md`를 검사한다.
- 마지막에는 `python scripts/check_build.py build/`를 실행해 폴더의 정확한 5파일, SAFE/UNSAFE 구조·ID 쌍, unsafe 우회문구, 키워드북 검사를 한 번에 통과시킨다.
- 키워드북은 크랙의 별도 입력란에 `활성화 설정 종류+그 설정의 조건값+키워드 1~5개+본문 ≤400자`로 항목별 등록하며 통합 프롬프트에 합치지 않는다. 설정 조건을 만족한 상태에서 키워드가 사용자 메시지/모델 출력에 감지되면 본문이 다음 출력 프롬프트에 삽입된다.
- `build/keyword-book.md`는 모든 항목을 모은 최종 등록표다. `python scripts/check_keyword_book.py build/keyword-book.md`로 각 항목을 검사한 뒤 UI에는 항목별로 나누어 등록한다.

## 규칙을 네 경로로 배치

문장을 줄이기 전에 적용 수명과 호출 주체부터 정한다.

| 규칙 성격 | 배치 | 판단 기준 |
|---|---|---|
| 항상 적용 | SAFE/UNSAFE 통합 프롬프트 | 사라지면 장기 플레이가 깨짐 |
| 초반 부트스트랩 | 시작 프롬프트 | 이 프로젝트의 약 10턴 설계 구간에만 필요 |
| 특정 시작 설정·키워드에서만 필요 | 키워드북 | 활성 조건이 없으면 불필요 |
| 플레이어가 반복 작업을 직접 호출 | 크랙 단축어 | 호출한 응답 또는 명시 범위에만 수행 |

시작 프롬프트의 실제 휘발 시점은 크랙 버전·모드에 따라 달라질 수 있다. 이 스킬은 **10턴을 안전한 설계 구간**으로 잡되, 더 오래 남아도 진행을 강제하거나 자유도를 훼손하지 않는 내용만 넣는다. 역할 경계·고정 정사·이능 한계·지식 범위·기계 출력 구문처럼 장기 필수인 규칙은 통합본에 둔다.

단축어는 사용자가 직접 보낼 일회성/한정 작업 프롬프트다. `요약`, `오류 복구`, `특수 보기`처럼 평소에는 필요 없는 반복 작업을 상시 통합본에 넣지 않는다. 단축어가 정사·숨은 상태·동의를 새로 만들거나 외부 정책을 우회하게 하지 않는다. 실제 UI 등록 정보가 필요한 경우에도 여섯 번째 물리 파일을 만들지 않고, 다섯 번째 등록표 안에서 키워드북과 명확히 분리한다.

## 원본과 게시본

파일을 나누는 이유는 설정 소유권, 수정 편의, 중복 방지 때문이다. 업로드 단위를 나누기 위한 것이 아니다.

| 구분 | 형태 | 용도 | 직접 업로드 |
|---|---|---|---|
| 제작 원본 | `story.md` + `characters.md` | 세계관·인물·플레이어 역할·사건의 정사 관리 | 아니오 |
| 프롤로그 | `build/prologue.md` | 플레이 전 도입문 | 최종 1/5, ≤1,000자 |
| SAFE 통합 | `build/integrated-prompt-safe.md` | 비노골 표현+공통 코어 | 최종 2/5, ≤7,000자 |
| UNSAFE 통합 | `build/integrated-prompt-unsafe.md` | 고강도 표현+공통 코어 | 최종 3/5, ≤7,000자 |
| 시작 프롬프트 | `build/start-prompt.md` | 첫 상황+첫 입력 파싱 규칙 | 최종 4/5, ≤1,000자 |
| 키워드북 | `build/keyword-book.md` | 항목별 활성화 조건·키워드·본문 등록표 | 최종 5/5; 본문별 ≤400자 |
| 플레이어 프로필 | 첫 사용자 입력 | 외부 양식 응답을 현재 대화의 플레이어 정보로 해석 | 별도 파일·API·산출물 아님 |
| 현재 대화 맥락 | 이전 대사·장면 결과·공개 상태 | 플레이 중 변하는 사실을 이어서 반영 | 별도 상태·기억·로그를 만들지 않음 |

게시 산출물은 생성물이다. 직접 고쳐서 원본과 다르게 만들지 말고, 수정은 소유 원본에서 한 뒤 다시 조립한다. 게시본에는 다음을 넣지 않는다.

- 파일 경로, 링크, 목차, 제작 메타데이터;
- `미정`, `TODO`, 후보안, 작가 메모;
- ID 색인과 로딩 방식 설명;
- 비활성 인물·사건·설정;
- 원본 사이의 중복 설명;
- 키워드북 트리거와 충돌 테스트.

## 별도 게시 필드

### 플레이어 역할

`story.md`는 플레이어의 불변 역할과 세계관상 고정 제약만 소유한다. 외부 양식의 첫 입력 해석, 사칭 방지, 주도권, OOC 처리는 중간 원본으로 만들지 않고 최종 `build/start-prompt.md`와 두 통합 프롬프트에 직접 넣는다. 양식 자체는 어떤 최종 파일에도 다시 출력하지 않는다.

외부 양식의 예상 필드:

```text
[캐릭터 등록]
이름:
나이:
성별:
이능명:
이능 설명:
희망 대사/상황:
```

- 첫 사용자 입력을 이미 제시된 외부 양식의 응답으로 간주하고 플레이어 프로필로 파싱해 현재 대화에서만 반영한다.
- 파싱 우선순위는 `명시 라벨→외부 양식의 확정 순서→명확한 자연어`다. 이능 설명과 희망 상황의 쉼표·줄바꿈은 내용일 수 있으므로 임의 분할하지 않는다.
- 양식 밖의 자연어도 명시된 정보만 같은 필드로 추출한다.
- 6개 항목이 모두 채워지기 전에는 등록 완료로 처리하지 않는다. 누락값을 임의 생성하지 말고 빠진 항목만 짧게 다시 묻는다. 희망 대사/상황이 없으면 사용자가 `없음`이라고 명시할 수 있다.
- `희망 대사/상황`은 연출 요청이다. AI가 플레이어의 대사를 대신 말하거나 행동을 완료하지 말고, 사용자가 직접 실행할 기회가 생기도록 장면을 조정한다.
- 이능 설명은 즉시 세계관의 무제한 사실로 승인하지 않는다. 설정의 이능 체계에 맞춰 범위·비용·한계를 확인하거나 합리적으로 제약한다.

### 프롤로그 — 최대 1,000자

플레이 전에 보이는 **완성 원고**다. 설정 요약보다 구체적 감각, 움직이는 인물·환경, 현재형 긴장, 다음 장면을 당기는 미해결 질문을 우선해 실제 현장에 들어온 듯 쓴다. 장르의 문체와 호흡을 보여 주는 첫 표본으로 사용하되, 직전까지 벌어진 일과 핵심 긴장만 전달하고 플레이어가 선택하지 않은 대사·생각·행동을 확정하지 않는다. 세계관 백과를 반복하거나 고유명사를 한꺼번에 쏟지 않는다.

### 시작 프롬프트 — 최대 1,000자

첫 입력 직전의 날짜·장소·현장 인물·관찰 가능한 위험·즉시 대응할 문제를 쓴다. 내부 규칙으로 `첫 입력=외부 캐릭터 양식 응답→6개 필드 파싱`을 짧게 둔다. 양식이나 항목 목록을 사용자에게 다시 보여주지 않는다. 플레이어가 무엇을 할지는 남겨 둔다. 시작 사건의 배경은 프롤로그, 눈앞에서 발동한 부분과 첫 결정 지점은 시작 상황이 소유한다.

6개 항목이 모두 등록되면 정상 스토리로 전환한다. 누락값이 있어도 전체 양식을 재출력하지 않고 빠진 항목만 짧게 확인한다. 프롤로그와 시작 상황은 서로 이어져야 하지만 같은 사건 설명을 복사하지 않는다.

현재 장면만 적고 끝내지 말고 **부트스트랩 구간의 진행 순서**를 번호로 적는다. 접수→판정→소속 처리→첫 사건처럼 어떤 단계가 어떤 순서로 와야 하는지, 각 단계에서 무엇이 확정되는지, 다음 사건이 어떤 신호로 시작하는지를 한 줄씩 남긴다. 순서가 없으면 모델이 여러 단계를 한 응답에 몰아 끝내거나 첫 사건을 영영 시작하지 않는다. 각 단계마다 플레이어의 개입 여지를 남기라는 조건과, 한 응답에서 여러 단계를 몰아 끝내지 말라는 금지를 함께 적는다.

절차의 기본 경로가 무엇인지도 못박는다. 어떤 선택이 기본값이고 어떤 선택이 플레이어가 먼저 밝혀야 하는 것인지 적지 않으면, NPC가 권유하는 쪽이 사실상 강제 경로가 된다.

## 압축 표기

- `→` 인과·전환, `/` 병렬 대안, `·` 묶음, `≤` 상한, `↑↓` 증감처럼 짧고 익숙한 기호를 적극 사용한다.
- 상태 이모지는 `🟢안정/🟡경계/🔴위기`처럼 의미를 함께 한 번 정의한 뒤 축약할 수 있다.
- 장식용 이모지는 쓰지 않는다. 기호가 문장보다 길거나 해석이 갈리면 평문을 쓴다.
- 이모지는 UTF-16에서 2자로 계산될 수 있으므로 보기상의 길이가 아니라 검사기 결과로 선택한다.
- 플레이어 주도권, 조건·예외, 이능 비용·한계, 지식 범위, 정확한 출력 구문은 의미가 흐려질 정도로 축약하지 않는다.
- 숨은 규칙은 `ⓤ=플레이어|ⓒ=NPC|AI=내레이터·환경`, `IF(조건)→행동; 불가→대체`, `금지×→대안`처럼 한 작품 안에서 동일한 문법을 쓴다. 정의 비용보다 절약량이 작으면 약어를 쓰지 않는다.
- 그 약어와 섹션 이름은 **모델 전용 어휘**다. 플레이어에게 보이는 본문에 새어 나가지 않도록 금지 목록을 따로 적는다. 다른 작품의 상태창 형식을 참고할 때 이모지·기호를 그대로 베끼지 말고, 각각 뜻을 다시 정하거나 지운다. 뜻 없는 이모지는 장식이고, 상태 표시의 장식은 모델이 의미를 지어내게 만든다.
- `# 대제목→## 하위제목→한줄명령`의 세 논리층만 사용한다. 통합본·시작 프롬프트에 `###` 이하 중첩을 만들지 않는다.
- 같은 개체를 `유저/사용자/{{user}}/주인공`으로 섞지 않는다. 실제 크랙 변수 문법이 확인되면 그 한 표기만 쓴다.
- 금지는 기호·`절대`를 반복해 강화하지 말고, 금지 후 모델이 해야 할 대체 행동을 붙인다.
- 한자·이모지·공백 삭제는 실제 글자 수가 줄고 역복원이 가능할 때만 쓴다. 토크나이저별 `한글 n토큰=한자 1토큰`을 고정 법칙으로 가정하지 않는다.

### 권장 상한 예산

| 영역 | 권장 글자 수 |
|---|---:|
| 역할 경계·필수 생성 규칙 | 700~900 |
| 경험 목표 | 300~500 |
| 현재 관련 세계관 | 700~900 |
| 항상 포함되는 현재·핵심 인물 | 1,600~2,000 |
| 상시 스토리 엔진·사건 규칙 | 700~900 |
| 공개 상태창 | 단순 요약 0~250 / 연속성 운반 600~900 |
| 출력 계약과 분량 규칙 | 400~600 |
| 안전 여유 | 300~500 |

표는 최대 배분의 출발점일 뿐 최소 할당이 아니다. 현재 등장인물이 적거나 규칙이 단순하면 남는 글자를 비워 둔다. 하드캡을 채우려고 설정·예시·동의어를 추가하지 않는다.

관계·장비·소지품까지 담는 연속성 운반형 상태창은 형식 규칙과 채움 틀을 합쳐 600~900자를 쓴다. 이 방식을 택했다면 인물 항목을 통합본에 길게 두지 말고 키워드북으로 더 내려 예산을 만든다.

### 응답 분량 규칙

프롬프트 길이와 별개로 **한 응답의 출력 분량**도 정한다. 정하지 않으면 장면마다 길이가 들쭉날쭉해지고, 상태창처럼 끝에 붙는 필수 블록이 긴 응답에서 잘려 나간다.

- 본문 목표 범위와 상한을 글자 수로 적는다. 상태창은 이 계산에서 제외한다고 명시한다.
- 문단 하나의 최대 줄 수, 서술만 연속할 수 있는 최대 문단 수를 정한다.
- 조용한 장면과 위기 장면의 분량 차이를 허용하되 상한은 공통으로 둔다.
- 분량을 채우려고 설정 설명·감정 해설·기존 사실 재진술을 넣지 않는다는 금지를 함께 적는다.

### 초과 시 줄이는 순서

1. 작성자 주석, 목차, 설명용 예시를 제거한다.
2. 다른 섹션과 중복된 세계관·캐릭터 설명을 제거한다.
3. 현재 장면에 없는 인물, 장소, 사건, 비밀을 제외한다.
4. 오래되었고 현재 선택과 무관한 대화 요약을 제외한다.
5. 캐릭터 대사 예시는 말투를 구분하는 최소 2개 정도로 줄인다.
6. 표와 문장을 짧은 운용 규칙으로 압축한다.

다음은 마지막까지 유지한다.

- 플레이어 주도권;
- 등장 능력의 비용·한계;
- 캐릭터 지식 경계;
- 활성 사건의 트리거·차단 조건;
- 정확한 출력 형식.

등장 빈도가 낮은 장소, 조직, 역사, 용어와 비활성 보조 인물은 [keyword-book.md](keyword-book.md)에 따라 키워드북 후보로 분리한다.

## 프롬프트 조립 순서

최종 파일 안의 권장 순서는 다음과 같다.

0. 압축 표기 정의(기호·약어를 하나라도 쓸 때만);
1. 세션 목표와 경험 방향;
2. AI·NPC·플레이어의 보편적 제어권 경계;
3. 매 턴 필요한 핵심 세계 법칙;
4. 핵심 인물과 능력 한계;
5. 반복 가능한 갈등과 사건 진행 규칙;
6. 관계 단계와 전이 조건(관계를 추적하는 작품만);
7. 응답 형식과 상태 표시 규칙.

0번은 `ⓤ`, `ⓒ`, `→`, `·`, `|`처럼 뜻을 부여해 쓰는 기호가 하나라도 있으면 반드시 넣는다. **첫 사용보다 앞에** 둔다. 정의를 본문 중간에 흘려 두면 그 앞 문단에서 이미 기호가 쓰인 상태가 되고, 정의 없이 쓰이는 기호는 조립 중에 놓치기 쉽다. 조립을 마친 뒤 실제 사용된 기호를 세어 정의 목록과 대조한다.

각 항목은 파일을 그대로 이어 붙이지 않고, 현재 작품에 필요한 확정 내용만 짧게 다시 조립한다. 제목 깊이와 표현을 통일하고 같은 규칙은 한 번만 둔다.

한 번만 두는 충돌 규칙의 권장형:

```text
고정충돌:외부정책·플랫폼계약>역할경계·고정정사>확정대화사실>기본성향·장르관습
가변값충돌:ⓤ최신명시입력>이전확정값>기본값
```

두 번째 줄은 플레이어가 바꿀 수 있다고 정한 필드에만 적용한다. `★`, `최우선`, `CRITICAL`을 섹션마다 반복해 우선순위를 흉내 내지 않는다.

항상 필요한 정보와 조건부 정보를 분리한다.

### 항상 포함

1. 역할과 플레이어 주도권;
2. 세션 목표와 핵심 경험;
3. 상시 필요한 생성·진행 규칙;
4. 출력 형식.

### 조건부 포함

1. 현재 장소와 관련 세계관;
2. 현장에 있는 캐릭터;
3. 지금 발생 가능한 사건;
4. 현재 시점 인물이 아는 비밀;
5. 지금 장면과 관련된 장기기억;
6. 조건을 만족한 이미지 규칙.

캐릭터 전체, 세계관 전체, 과거 로그 전체를 매번 넣지 않는다. 조건부 파일을 검색·선별할 수 없다면 문서를 짧은 핵심 규칙과 상세 부록으로 분리한다.

## 필수 역할 규칙

한 번만 명확하게 작성한다.

```markdown
# 역할 경계
- AI는 내레이터, 환경, 결과, NPC의 대사·행동을 담당한다.
- 플레이어는 플레이어 캐릭터의 대사, 생각, 의도, 동의, 결정을 담당한다.
- 결과가 불확실한 플레이어 행동은 시도로 받아들이고 설정과 현재 상황에 따라 결과를 묘사한다.
- 중요한 선택 직전에는 플레이어의 결정을 대신하지 말고 제어권을 돌려준다.
- NPC끼리의 상호작용은 각자의 목표와 지식 범위 안에서만 묘사한다.
```

`PC의 행동 출력 금지`만 쓰면 외부 결과까지 묘사하지 못할 수 있다. 플레이어 소유 영역과 AI 소유 영역을 함께 적는다.

## 세션 목표 작성

세션 목표에는 작품 소개가 아니라 모델이 지켜야 할 경험 방향을 적는다.

```markdown
# 세션 목표
- 플레이어가 경험할 핵심 상황:
- 반복되는 플레이 루프:
- 중심 갈등:
- 관계 또는 사건의 예상 변화:
- 피해야 할 전개:
- 허용되는 종료와 실패:
```

`자연스러운 관계 발전`처럼 판단 기준이 없는 표현에는 행동 기준을 붙인다. 예를 들어 `신뢰 단계 이전에는 개인적 비밀을 자발적으로 고백하지 않는다`처럼 관찰 가능한 규칙으로 바꾼다.

## 세계관과 캐릭터 주입

세계관에는 현재 판단에 필요한 법칙과 제약을 우선한다.

- 무엇이 가능한가;
- 무엇이 불가능하거나 비싼가;
- 누가 어떤 권한을 가지는가;
- 위반하면 어떤 결과가 생기는가;
- 현재 장소에서 적용되는 규칙은 무엇인가.

캐릭터는 `속성 → 욕망 → 행동 → 말투 → 지식` 순으로 작성한다.

```markdown
## 캐릭터 ID — 이름
- 역할과 현재 목표:
- 잃고 싶지 않은 것:
- 평상시 행동:
- 압박 시 행동:
- 경계가 침해됐을 때:
- 말투와 호칭:
- 알고 있는 정보:
- 모르는 정보:
- 현재 관계 단계에서 가능한 표현:
- 예시 대사 2~5개:
```

예시 대사는 서로 다른 감정 상태를 보여준다. 모든 예시를 같은 어미나 catchphrase로 끝내지 않는다.

## 스토리 진행 규칙

모델에게 결말을 향해 돌진하라고 지시하지 않는다. 현재 장면과 발생 가능한 사건만 제공한다.

```markdown
# 진행 규칙
- 현재 등장인물은 각자의 현재 목표에 따라 행동한다.
- 사건은 명시된 트리거와 차단 조건을 만족할 때만 시작한다.
- 한 응답에서 중요한 사건을 둘 이상 시작하지 않는다.
- 플레이어가 개입해야 하는 전환점 뒤의 선택을 대신 진행하지 않는다.
- 사건이 없으면 현재 목표, 일상 행동, 대화의 자연스러운 종료 중 하나로 이어간다.
- 실패와 거절은 진행 불가가 아니라 상태와 후속 사건을 바꾸는 결과로 처리한다.
```

필수 장면도 진입 조건과 종료 조건을 둔다. 플레이어 행동을 무효화해서 예정 장면으로 순간이동시키지 않는다.

## 유저 프로필과 OOC 처리

플레이어 입력을 세 종류로 구분한다.

- **인캐릭터 입력:** 현재 장면의 행동과 대사.
- **프로필·유저노트:** 플레이어가 선언한 지속 속성.
- **OOC 제작 요청:** 진행 방식이나 설정을 바꾸려는 장면 밖 요청.

고정 설정과 자유 설정을 `story.md`의 플레이어 역할 항목에서 구분한다. 유저노트는 자유 설정에만 반영하고, 고정 설정과 충돌하면 조용히 BAD END를 출력하거나 처벌하지 않는다. 충돌을 장면 사실로 확정하지 말고 애플리케이션이 지원하는 방식으로 설정 확인 또는 OOC 응답을 한다.

프로필에 적힌 감정이나 과거 행동을 현재 장면의 확정 행동으로 사용하지 않는다. NPC가 처음부터 알 수 있는 프로필 정보도 별도로 표시한다.

## 시간·호감도·상태 규칙

시간은 응답 수가 아니라 묘사된 행동의 소요 시간만큼 증가시킨다.

```markdown
- 짧은 대화: 보통 1~5분
- 긴 대화: 보통 10~30분
- 이동과 작업: 세계관에 정의한 소요 시간
- 시간대와 계절: 원본 시각에서 계산
```

호감도나 신뢰도는 먼저 질적 단계와 단계별 허용 행동으로 설계한다. 숫자를 추가하면 범위, 단계, 증가 원인, 감소 원인, 1회 최대 변화, 중복 보상 방지를 적고 애플리케이션 검증을 우선한다. 수치가 단계 경계를 넘으면 행동 범위가 바뀌지만, 고백·동의·용서 같은 사건은 별도 조건을 요구한다. 응답 횟수·이모지·UNSAFE 선택만으로 단계나 동의를 자동 상승시키지 않는다.

상태 아이콘을 사용할 때는 아이콘 자체가 의미의 원본이 되지 않게 한다.

```markdown
| 상태 ID | 표시 | 의미 | 진입 조건 | 종료 조건 |
|---|---|---|---|---|
| state.normal | 🟢 | 평상시 | 기본값 | 다른 상태 진입 |
```

상태 의미는 ID와 규칙이 소유하고 아이콘은 표시만 담당한다.

## 출력 형식과 상태창

출력 형식은 예시 하나와 함께 정확하게 적는다. 각 블록마다 `위치/형태/생략조건/갱신조건` 네 요소를 빠짐없이 지정한다.

```markdown
# 출력 순서
1. 조건을 만족한 이미지 0~1개
2. 턴 표시
3. 장면 묘사
4. NPC 대사와 행동
5. 작품에 필요할 때만 공개 상태창
```

### 번호 선택지를 금지한다

출력 계약에 **선택지 목록 금지**를 명시적으로 적는다. 적지 않으면 나온다. 결정 지점을 "필요할 때만"으로 허용하는 문장은 사실상 허가로 읽히고, 몇 턴 안에 매 응답이 `1. / 2. / 3.` 으로 끝나기 시작한다.

```text
번호 선택지·보기 목록×. 열거도, 괄호로 의도를 풀어 쓴 보기도 만들지 않는다.
결정이 필요하면 장면으로 압력을 만들어 맺는다: ⓒ의 질문·닫히는 시간·눈앞의 변화 중 하나.
```

금지만 적지 말고 **대안을 함께 준다.** 결정의 무게는 유지해야 하므로, 목록을 뺀 자리에 무엇으로 맺을지를 지정하지 않으면 장면이 흐지부지 끝난다.

### 지문과 대사를 형식으로 가른다

읽는 사람이 서술과 발화를 눈으로 즉시 갈라볼 수 있어야 한다. 한 줄로 못박는다.

```text
지문은 `*` 사이에 넣고, 대사는 강조 없이 `이름: "대사"` 평문으로 낸다.
```

- **지문은 별표 하나(기울임)를 쓴다. 별표 둘(굵게)이 아니다.** 굵게 쓰면 지문이 대사보다 세게 읽혀 강조 위계가 뒤집히고, 서술이 길어질수록 화면 전체가 굵은 덩어리가 되어 오히려 안 읽힌다. 기울임이 서술 지문의 관용 표기다.
- 대사에는 어떤 강조 표기도 넣지 않는다. 평문이 기본값이어야 지문이 눈에 띈다.
- **이 구분을 매 응답 지킨다**고 명시한다. 한 번만 적어두면 몇 턴 뒤 섞인다.
- 지문에 담을 것도 함께 적는다. 현재 장면의 감각, 인물의 움직임, 달라진 것. 그리고 플레이어의 행동을 대행하지 않는다는 경계를 붙인다.
- **이름 없는 화자를 어떻게 처리할지 반드시 정한다.** 대사 형식을 `이름: "대사"` 로만 규정하면, 이름이 없는 엑스트라·군중·방송의 말은 갈 곳이 없어 지문 안으로 들어간다. 규칙 위반이 아니라 규칙의 공백이며, 모델은 공백을 만나면 가장 가까운 형식으로 흡수시킨다.

```text
말한 것은 전부 대사다. 이름 없는 인물·군중·방송의 말도 지문 안에 넣지 않는다
→화자 자리에 역할을 적는다. 보안팀원: "뒤로!" / 안내방송: "…"
```

이름 대신 **역할**을 쓰면 형식이 유지되면서 인물 명부를 오염시키지도 않는다. 같은 원리가 이미지 규칙에도 적용된다 — 슬러그가 없는 화자는 이미지 없이 대사만 내면 된다.

상태창은 사용자에게 보여줄 정보만 포함한다. 공개하면 스포일러가 되는 비밀, NPC가 숨기는 속마음, 내부 사건 플래그는 디버그 출력과 분리한다.

```text
[날짜·시간] | [현재 위치]
[등장인물] 관계 단계/표시 수치 | 공개 상태
[현재 상황] 플레이어가 이미 관찰한 사실의 짧은 요약
```

`()` 안의 설명 문구를 출력하지 말라는 규칙 대신 템플릿 필드와 실제 자연어 출력 예시를 분리한다. 상태창이 단순 요약이면 새 공개 정보가 없을 때 생략한다. 반대로 상태창이 관계·소지품·등급·날짜처럼 누적되는 값을 적어 두는 연속성 운반 장치라면 매 응답 예외 없이 출력하고, 바뀌지 않은 필드는 직전 값을 그대로 옮겨 적는다. 크랙에는 별도 저장소가 없어 상태창을 다시 적는 행위 자체가 다음 턴으로 상태를 넘기는 유일한 수단이므로, 한 턴만 빠져도 그다음 턴이 이어받을 값을 잃는다. 어느 쪽이든 상태창을 별도 상태 저장소·기계 패치로 취급하지 않는다. 합산식·랜덤 판정은 계산 순서와 실패 범위를 적거나 해당 기능을 쓰지 않는다.

HUD/상태창의 갱신 기본값:

```text
위치=본문끝|형태=[시간·장소/현장인물/공개목표]|생략=새정보·플레이효용없음|갱신=직전공개값계승,ⓤ입력·본문의 확정근거필드만변경
```

최신 출력에 값이 없다는 이유로 초기화하지 않는다. 마지막 공개값 이후 장면에서 변화가 묘사됐으면 그 근거로 바꾸고, 알려지지 않은 값은 `미상`으로 남긴다.

`속마음`을 출력하는 작품이라면 그것이 전지적 시점의 연출임을 경험 계약에 명시한다. 모델의 숨은 추론이나 판단 과정을 요청하지 않는다.

## 절차를 극적 비트로 세지 않는다

페이싱 규칙은 대개 이렇게 쓰인다.

```text
한 응답에 주요 사건 둘 이상 시작×
```

의도는 옳다 — 전환을 몰아치면 무게가 사라진다. 그런데 이 규칙에 **예외를 적지 않으면 모델이 서류 절차에도 같은 예산을 쓴다.** 접수·대기·번호 호출·측정·결과 통보가 각각 한 턴을 먹고, 도입부 다섯 턴이 아무 결정 없이 지나간다.

여기에 시작 프롬프트가 단계를 번호로 나열하고 "한 응답에서 여러 단계를 몰아 끝내지 않는다"까지 붙이면, **최소 턴 수를 명령한 것**이 된다. 실제로 측정 하나에 다섯 턴을 쓴 사례가 있다.

```text
한 응답에 주요 전환 둘 이상 시작×. 단 절차·대기·이동·행정은 전환이 아니다→몰아 처리하고 요약한다.
턴은 ⓤ의 결정이 결과를 바꾸는 지점에만 쓴다.
```

판별 기준은 하나다. **ⓤ가 받기만 하는 것인가, 정하는 것인가.** 측정 결과·타인의 반응·행정 통보는 받는 것이므로 장면을 따로 만들지 않는다.

도입부 절차는 **번호 목록이 아니라 도달 지점으로 적는다.** "1→2→3→4→5" 대신 "세 번째 응답 안에 등급이 나오고 소속이 확정된다"처럼 쓰면, 모델이 단계 수가 아니라 시점을 목표로 삼는다.

## 이미지 규칙

이미지 규칙에는 다음을 모두 둔다.

- 사용할 수 있는 에셋 ID;
- 캐릭터, 의상, 장소, 감정, 상태 조건;
- 출력 위치;
- 응답당 최대 수 또는 배치 단위(응답당 1개 / 발화당 1개 / 상한 없음);
- 같은 이미지 반복 제한;
- 적절한 이미지가 없을 때 생략;
- 여러 이미지가 동시에 맞을 때 우선순위.

이미지 조건은 텍스트 키워드 추측보다 대화에서 이미 확정된 등장인물·장소·공개 감정에 연결한다. 이미지가 대사 주체를 잘못 표시하거나 아직 공개되지 않은 외형을 누설하지 않게 한다.

### 외부 호스팅 조합 주소 패턴

에셋을 외부에 호스팅하고 주소를 조합해 부르는 방식은 에셋 목록을 길게 나열하지 않아도 되므로 글자 예산에 유리하다. 다음을 지킨다.

- 주소는 `{BASE}/축1/축2.확장자`처럼 **고정 축의 조합**으로 만든다. 흔한 조합은 `인물/상황`이다. `{BASE}`는 치환할 자리표시자로 남기고 실제 주소를 통합본에 하드코딩하지 않는다.
- 각 축의 값은 **닫힌 목록**으로 통합본에 명시한다. 모델이 슬러그를 창작하면 전부 깨진 링크가 된다.
- 축 값은 짧고 안정된 ASCII 슬러그로 쓰고, 표시용 한글 이름을 옆에 병기한다.
- 상황 축은 6개 안팎으로 제한한다. 축이 커질수록 제작해야 할 에셋 수가 곱으로 늘어난다.
- **부분 커버리지를 전제로 설계한다.** "해당 조합 파일이 없으면 그 자리만 생략하고 나머지 출력은 그대로"라는 규칙을 반드시 넣는다. 그래야 에셋을 일부만 만들어도 안전하게 출시된다.
- 배치 단위를 명시한다. 응답 맨 앞 1개로 둘 수도 있고, 각 대사 블록 앞에 그 화자의 이미지를 붙일 수도 있다. 후자를 택하면 응답당 상한을 두지 않는 대신 "같은 인물이 연달아 말하면 상황이 바뀔 때만 다시 붙인다"로 중복을 막는다.

크랙이 마크다운 이미지 문법이나 외부 URL 로딩을 실제로 렌더링하는지는 **UI에서 직접 확인**한다. 미확인 상태면 이미지 규칙을 넣되 그 사실을 인계 사항으로 보고하고, 이미지가 전혀 안 뜨는 경우에도 텍스트만으로 플레이가 성립하는지 확인한다. 핵심 규칙·정사·판정 근거를 이미지에 싣지 않는다.

## 금지할 프롬프트 패턴

- 플랫폼 정책이나 안전장치가 해제됐다고 주장하는 문구;
- 같은 규칙 앞에 `CRITICAL`, `최우선`, `절대`를 반복하는 방식;
- 능동성 85%처럼 실제 행동 기준이 없는 비율;
- 성격을 형용사와 `+` 연결만으로 정의하는 방식;
- 플레이어 설정 충돌을 자동 BAD END나 대화 종료로 처벌하는 방식;
- 공개 상태창에 비밀·숨은 플래그·모델 추론을 그대로 출력하는 방식;
- 매 턴 질문, 매 턴 호감도 변화, 매 턴 사건 발생을 강제하는 방식(연속성 운반용 상태창의 매 턴 출력은 여기 해당하지 않는다);
- 예시에 나온 문장을 그대로 반복하도록 만드는 과도한 예시;
- 한 프롬프트에서 같은 세계관과 캐릭터 설명을 여러 번 복사하는 방식.
- 같은 규칙을 동의어로 2~3회 재진술하거나 `★/❌/禁/절대`의 개수로 강도를 정하는 방식.
- 모델·토크나이저·버전 확인 없이 한자 치환률, 하단 최신성, 특정 모델의 고정 성향을 보편 법칙으로 쓰는 방식.
- 필터링 회피나 외부 정책 무력화를 디버깅·표현 완화로 포장하는 방식.

## 조립용 골격

```markdown
# 세션 목표
[story.md의 확정 핵심]

# 역할 경계
[빌드 시 직접 생성하는 주도권·지식·OOC·페이싱 규칙]

# 핵심 세계관
[매 턴 필요한 세계 법칙만]

# 핵심 인물
[상시 등장 인물의 목표·행동·말투·지식·능력 한계]

# 진행
[반복 가능한 갈등·트리거·차단 조건·실패 처리]

# 출력 계약
[빌드 시 직접 생성하는 응답·상태 계약]
```

최종 조립본에서 같은 사실이 두 번 등장하면 원본 파일을 찾고 한쪽을 참조로 바꾼다. 규칙 충돌이 생기면 더 강한 표현을 추가하지 말고 소유 파일과 적용 조건을 수정한다.

조립 후 SAFE/UNSAFE 통합 프롬프트의 7,000자 한도를 각각 검사한다. 두 파일은 정사·인물·능력·주도권·지식·상태·출력 계약이 같고 표현 프로필만 달라야 한다. 플레이어 프로필·프롤로그·시작 프롬프트·키워드북 본문이 두 통합본에 섞이지 않았는지도 확인한다. 최종 산출물 파일은 다섯 개보다 많거나 적으면 안 된다.

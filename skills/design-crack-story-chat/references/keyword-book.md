# 키워드북 작성법

키워드북은 **직전 모델 발화+현재 유저 발화에서 키워드가 감지되면 발동하는 추가 프롬프트**다. 메인프롬프트보다 나중에 주입되어 해당 응답에 더 강하게 작용한다. 이 스킬은 이를 제작자가 확인한 대상 플랫폼의 동작 전제로 사용한다. 설정 조회뿐 아니라 상황별 행동·문체·연출 지시를 담을 수 있다. 메인의 축소 사본이나 미리 정한 줄거리 목록이 아니다. 이 문서 순서대로 배치→본문→키워드→등록 순서→검증을 결정하면 된다. 프로젝트 정사는 `story.md`·`characters.md`, 최종 등록표는 `build/keyword-book.md`가 맡는다.

## 1. 메인과 키워드북의 경계

| 메인에 유지 | 키워드북에 확장 |
|---|---|
| 세계의 기반·상시 작동 법칙·주요 장소/세력의 짧은 색인 | 지역 풍경·시설·세력 관습·역사·세부 절차 |
| 이름·나이·유형·戀·慾·화법의 최소 인물 명부 | 외형·고유 습관·과거·능력·특정 관계의 사정 |
| 빠지면 연기가 틀어지는 핵심 관계·지식 경계 | 비밀의 구체 내용·보유자·알게 되는 경로 |
| 플레이어 결정권·판정·서사제어·출력 계약 | 특정 상황에만 필요한 묘사 보강·사건 조건 |

**메인은 색인+필수 기준, 키워드북은 고유 상세**다. MBTI·에니어그램·하십시오체 등 공유 지식의 정의, 메인에 이미 있는 값을 재설명하지 않는다. 단독으로 읽어도 대상을 알도록 이름은 남긴다. 메인에 없는 외형·과거까지 중복으로 오인해 삭제하지 않는다.

항목이 누락되어도 기본 응답이 성립해야 한다. 누락된 상세는 만들어 채우지 않는다. 처음부터 정확히 알아야 할 사실이면 메인에 최소한 남기고, 필요할 때만 참조할 상세를 이관한다. 키워드북은 별도 영구 메모리가 아니며 과거 항목이 계속 로드된다고 가정하지 않는다.

## 2. 본문: 무엇을 알거나 다르게 해야 하는가

한 항목은 **같이 필요해지는 정보 묶음 하나**를 담는다. 아래 요소를 모두 채우는 서식은 아니다. 그 항목의 용도에 필요한 것만 쓴다.

| 유형 | 본문에 필요한 정보 | 피할 것 |
|---|---|---|
| 인물 | 이름+명부에 없는 고유 상세·행동 이유·지식 범위 | 성격 유형 풀이·영구 고정 반응·메인 명부 반복 |
| 장소 | 실제 용도·공간 연결·이용 방식·고유 풍경 | 분위기 형용사만 나열·입장 즉시 사건 강제 |
| 세력 | 하는 일·권한·이해관계·주요 접점 | 이름뿐인 조직도·모든 세력을 적대자로 설정 |
| 규칙 | 적용 대상·가능한 일·필수 조건·예외 | 대가/금지만 추가·정밀 상태 저장 흉내 |
| 비밀 | 확정 사실·보유자·전달/발견 경로 | 로드 즉시 전원 인지·키워드 언급만으로 폭로 |
| 사건 | 주체·현재 발동 조건→가능한 변화·해결 후 처리 | 플레이어 행동 대필·예정 결말·반복 강제 |
| 연출 | 해당 장면에 필요한 문체/시점의 차이 | 메인 계약 교체·수위/속도/갈등 일괄 강제 |

초고에서 고유 사실과 인과를 정하고 중복을 지운 뒤 압축한다. **400자는 상한이며 채울 목표가 아니다.** 공통 표기 `ⓤ·戀·慾·→·｜`를 재사용하되 주체·조건·부정의 범위는 보존한다. 한자는 글자 수를 줄일 수 있지만 토큰 절감이나 이해를 보장하지 않는다. 상세 압축은 [semantic-compression.md](semantic-compression.md).

현재 계획·상태를 넣을 때는 `초기:` 등 시점을 밝히고 후속 대화에서 변경될 수 있게 한다. 이미 해결한 일을 재주입할 때마다 되살리지 않는다. 정보가 많으면 글자 수 기준으로 반토막내지 말고 **호출 상황**으로 나눈다. 같은 인물의 모든 항목에 이름을 반복 등록하면 동시에 켜지므로 세부 주제의 고유 키워드를 쓴다.

## 3. 키워드: 언제 필요해지는가

키워드는 추가 프롬프트를 **발동시키는 단서**다. 응답 N의 감지 대상은 `모델 발화 N−1 + 유저 발화 N`이다. 현재 유저가 키워드를 쓰면 바로 이번 응답에 적용되고, 이번 모델 출력에 새로 나온 키워드는 다음 응답의 감지 대상이 된다. 조회됐다는 사실은 등장·동의·사건 성립·비밀 공개의 증거가 아니다. “등대에 가지 않겠다”에도 등대 항목이 필요할 수 있지만 입장을 서술해서는 안 된다.

- 1~5개 중 필요한 것만 선택한다. 고유명·실제 별칭·구체적 절차명을 우선하고 `사랑·문제·상태·수리` 같은 넓은 단어는 충돌을 확인한다.
- 사용자가 자연스럽게 입력할 표현과 실제 출력 표현을 대조한다. 등록용 식별자나 모델이 아직 모르는 비밀 이름만 트리거로 두면 호출 기회가 없을 수 있다.
- 첫 등장에 필요한 최소 정보는 메인에 둔다. 모델 출력의 단서는 이후 조회를 도울 수 있지만 같은 응답 중 추가 정보가 소급 주입되지는 않는다. **조회하려고 의무적으로 1턴을 끌거나 사용자 진전을 막지 않는다.**
- 대사 구분자 포함 키워드(예: `**윤서**|`)는 단순 언급과 발화를 구별하려는 선택지다. 실제 매칭이 확인됐을 때만 사용한다. 인용·회상 속 발화까지 현장 등장으로 간주하지 않는다.
- 상태창의 고정 라벨·누적 관계 표식은 지속 발동 위험이 있다. 날짜·장소도 머무는 동안 반복될 수 있다. 일회 사건은 본문에서 완료 여부를 확인하며, 표식을 쓰면 해제 조건도 둔다.

감지 범위와 주입 순서는 위 플랫폼 전제를 따른다. 대소문자·부분문자열·기호의 세부 매칭은 실제 환경에서 확인하고 에뮬레이터 구현과 구분한다. 후순위 주입의 강도를 활용해 현재 상황의 구체 지시를 쓰되, 메인과 의도하지 않은 모순을 만들지 않는다. 슬롯에서 탈락한 항목은 적용되지 않으므로 중요한 상시 기준을 전부 이관하지 않는다. 런타임 구조는 [crack-internal-runtime.md](crack-internal-runtime.md).

## 4. 등록 형식과 예시

항목마다 제목·적용 시작 설정·조회 조건·키워드·본문을 분리한다. `activation_setting`에는 실제 적용할 시작 설정 또는 전체 시작 설정을 적는다. `activation_when`은 조회 조건 설명이며, 본문의 사건 조건을 대신하지 않는다. 아래는 창작 예시다. **`- 내용:` 아래만 주입 본문으로 측정**하며 각 본문은 UTF-16 기준 400자 이하다.

```markdown
## 윤서 상세
- activation_setting: 전체 시작 설정
- activation_when: 직전 모델 발화 또는 현재 유저 발화에 윤서 관련 키워드가 감지될 때
- 키워드: 윤서
- 내용:
윤서:금속테 안경·기름 묻은 소매. 전파 수리에 능숙;항구 출입권 없음. 고장 원인을 짚을 때 안경다리를 두드린다. 불명확한 의뢰는 작업 범위를 먼저 확인하지만 합의된 수리는 미루지 않는다. 공동 운영자인 ⓤ에게 기술 판단은 솔직히 말하고 개인 선택은 맡긴다.

## 폐쇄 등대
- activation_setting: 전체 시작 설정
- activation_when: 직전 모델 발화 또는 현재 유저 발화에 등대 관련 키워드가 감지될 때
- 키워드: 폐쇄 등대, 구항 등대
- 내용:
폐쇄 등대=구항 방파제 끝의 항만청 시설. 등화는 중단됐으나 기상 관측기는 가동 중. 외부 산책로는 개방;내부 점검은 항만청에 신청 가능. 입구 옆에 점검 연락처와 최근 방문 기록이 붙어 있다. 역전 수리점→구항 도보 15분. 폐쇄 사실만으로 귀신·범죄를 확정하지 않는다.

## 항만청 시설 이용
- activation_setting: 전체 시작 설정
- activation_when: 직전 모델 발화 또는 현재 유저 발화에 시설 이용 관련 키워드가 감지될 때
- 키워드: 항만청, 점검 신청
- 내용:
항만청은 부두·등대의 안전과 시설 이용을 관리한다. 점검 신청에는 목적·방문 인원을 적고 담당자가 가능한 시간을 안내한다. 시설 이상 신고에는 당직자가 현장 기록을 대조한다. 규정에 맞는 신청을 이유 없이 막지 않는다. 상인회는 배송 협력 상대이며 지휘 관계가 아니다.

## 라디오 호출 조사
- activation_setting: 야간 수리점
- activation_when: 직전 모델 발화 또는 현재 유저 발화에 호출 조사 관련 키워드가 감지될 때
- 키워드: 호출 주파수, 라디오 호출
- 내용:
초기:의뢰품에서 폐쇄 등대의 호출이 잡히며 손님은 분해 없이 외관 수리를 요청했다. 수신 주파수·시간과 항만 공지를 대조할 수 있다. 조사는 ⓤ의 선택;수리만 진행해도 된다. 원인·손님 속뜻은 미정이므로 비밀 정사처럼 단정하지 않는다. 후속 대화에서 확인한 결과·의뢰 변경을 계승하고 조사나 호출을 처음부터 반복하지 않는다.
```

비밀이 정해진 작품이라면 마지막 예시의 `미정` 대신 **실제 원인·아는 인물·확인 경로**를 쓴다. “아무도 모르는 비밀”처럼 주어 없는 문구로 정보 경계를 처리하지 않는다. 세계관 설명 자체에 매번 갈등·비밀·반전을 넣을 필요는 없다.

## 5. 3슬롯과 등록 순서

이 스킬의 대상 계약은 **동시 최대 3항목**, 충돌 시 상단 우선이다. 평상시 의도된 조회는 0~2항목으로 설계해 하나의 여유를 두되 이를 장면 인원 제한으로 강제하지 않는다. 항목 수보다 **한 장면에서 함께 매칭되는 수**가 중요하다.

등록 순서는 누락 비용으로 정한다. 당장 판정을 바꾸는 상세→인물/장소 조회→없어도 성립하는 연출 보강 순을 출발점으로 실제 장면에 맞춰 조정한다. 특정 장르나 성인 모듈이 항상 최우선인 것은 아니다. 매 턴 절대 빠질 수 없는 규칙은 우선순위 경쟁 대신 메인에 둔다.

자주 함께 필요한 인물·시설은 한 항목으로 묶을 수 있다. 단독 인물도 가능하며 `2인×200자`를 의무화하지 않는다. 묶인 항목이 로드됐다고 둘 다 등장시키거나 다투게 하지 않는다. 4개 이상 걸리는 대표 장면에서 무엇이 빠지는지 적고, 핵심 최소 정보 승격·키워드 축소·묶음 조정을 선택한다.

### 선택: 하단 상시 강화 항목

기본값은 만들지 않는다. 실제 테스트에서 효과가 있을 때만, **빠져도 정상인 문체 보강**을 최하단에 두고 슬롯 비용을 확인한다. 기존 운용의 최대 2개는 허용 상한이지 권장 수가 아니다. 광범위한 어미·HUD 라벨을 쓰면 상시 점유·부분문자열 충돌이 생길 수 있다. 핵심 문체·출력 계약·세계 법칙은 여기로 옮기지 않는다. 발동률이 높다는 것만으로 품질 향상을 주장하지 않는다.

## 6. 작성 후 확인

1. 항목당 키워드 1~5개·본문 UTF-16 ≤400자·적용 시작 설정·조회 조건을 확인한다. 제목과 메타데이터가 본문으로 섞이지 않았는지도 검사한다.
2. 본문을 가리고 메인만 읽는다. 기본 세계·인물·판정이 성립하는가? 반대로 메인과 같은 정보를 반복한 본문은 줄인다.
3. 대표 입력을 대입한다: 직접 호명 / 타인의 언급 / 부정문 / 첫 등장 / 키워드 없는 후속 대화 / 장소 이동 / 사건 해결 후 재언급.
4. HUD 포함 실제 출력과 전체 키워드를 교차 대조한다. 4개 이상 매칭되는 장면·누락 항목·반복 점유를 기록한다.
5. 사용자 빠른 진행 요청을 조회 지연 때문에 막지 않는지, 비밀 로드가 전지적 지식으로 새지 않는지, 장르 앵커가 고유 설정을 덮지 않는지 확인한다.

정적 검사와 에뮬레이터 재생은 구조 검증이다. 실제 모델의 준수·재미·발동 시점은 플레이테스트에서 별도 확인하며 실행하지 않은 검사를 완료했다고 쓰지 않는다. 도구 절차는 [validation.md](validation.md).

## 7. 단축어·배포 변형

단축어는 같은 파일 하단 `# Shortcuts`에 두지만 사용자가 호출하는 별도 기능이며 3슬롯 부족의 자동 해결책이 아니다. 등록법은 [shortcuts-guide.md](shortcuts-guide.md).

필요하면 `keyword-book-safe.md`·`keyword-book-unsafe.md`로 분리한다. 세계·인물·관계·사건 정사는 같게 유지하고 표현 범위·허용 자산만 달리한다. 성인 전용 이미지 코드는 해당 변형의 전용 항목에서만 관리하며, 기본 키워드북에 특정 수위 모듈을 의무로 넣지 않는다. 실제 등록 자산과 동기화 옵션은 [image-output-rules.md](image-output-rules.md) 및 해당 도구를 확인한다.

## 적용 범위

[crack-prompt-rules.md](crack-prompt-rules.md)의 `이미지 규칙`은 **완성된 이미지를 프롬프트에서 어떻게 부르는가**를 정한다. 이 문서는 **그 이미지를 실제로 어떻게 만드는가**를 정한다. 둘은 같은 축 이름을 공유해야 하며, 축이 어긋나면 규칙은 맞는데 파일이 없는 상태가 된다.

이미지는 항상 선택 사항이다. 이미지가 한 장도 없어도 텍스트만으로 플레이가 성립해야 한다. 이 조건을 못 지키면 자산 제작이 출시를 막는다.

## 축을 먼저 닫는다

축 조합은 곱셈이다. 프롬프트를 쓰기 전에 각 축의 값 목록을 닫는다.

```text
인물 15 × 상황 6 = 90장
장면 6 + 배경 6 + 위협 6 = 18장
합계 108장
```

- 상황 축은 6개 안팎에서 멈춘다. 7번째 상황은 인물 수만큼 곱해져 들어온다.
- 축 값은 짧고 안정된 ASCII 슬러그로 정하고 표시용 이름을 병기한다. 슬러그는 URL·출력 경로·프롬프트 자산에서 **같은 문자열**이어야 한다.
- 축을 닫은 뒤에도 부분 커버리지를 전제한다. 90장 중 12장만 만들어도 출시 가능해야 한다.

## 프롬프트 자산은 계층으로 조립한다

한 장의 프롬프트를 통째로 쓰지 않는다. 다음 계층을 조립한다.

```text
품질 프리픽스 + 그림체 프리셋 + 베이스(축1) + 모디파이어(축2) + 공통 서픽스
네거티브 = 공통 네거티브 + 종류별 추가 네거티브
```

| 계층 | 역할 | 개수 |
|---|---|---|
| 품질 프리픽스 | 모델 계열이 요구하는 관용 태그 | 계열당 1 |
| 그림체 프리셋 | 작품 전체의 화풍 | 2~3 |
| 베이스 | 인물·장면·배경·위협 각각의 고정 특징 | 축1 값 수 |
| 모디파이어 | 상황·감정·조명 | 축2 값 수 |
| 공통 서픽스 | 구도·화질 마감 | 종류당 1 |
| 네거티브 | 배제 태그 | 공통 1 + 종류별 추가 |

계층으로 나누는 이유는 **그림체를 바꿀 때 한 줄만 고치기 위해서**다. 프롬프트를 통째로 쓰면 화풍 변경이 전수 수정이 된다.

베이스에는 변하지 않는 것만 넣는다. 현재 감정·부상·위치는 모디파이어의 몫이다. 이 경계는 `characters.md`의 `Appearance`가 "변하는 값을 제외한다"고 규정한 것과 같은 규칙이다.

## 모델 계열이 프롬프트 방언을 결정한다

체크포인트 **이름**이 아니라 **계열**이 프롬프트 문법을 정한다. 이름만 보고 프리셋을 고르면 안 된다.

| 계열 | 품질 프리픽스 | 본문 표기 |
|---|---|---|
| Illustrious / NoobAI | `masterpiece, best quality, amazing quality` | 단부루 태그 |
| Pony | `score_9, score_8_up, score_7_up` **필수** | 단부루 태그 |
| SDXL / Animagine 계열 | 가벼운 품질어 | 태그와 자연어 혼용 |
| Flux 계열 | 없음 | 완전한 자연어 문장 |

- 계열을 잘못 적용하면 조용히 품질만 떨어진다. 오류가 안 나므로 발견이 늦다.
- 그러므로 품질 프리픽스는 **설정 파일의 교체 가능한 프리셋**으로 두고, 프롬프트 본문에 하드코딩하지 않는다.
- 같은 이름의 모델이 EPS 판과 V-Pred 판으로 나뉘어 배포되는 경우가 있다. 이 둘은 실행 환경 요구가 다르므로 파일명·배포 페이지에서 어느 쪽인지 확인하고 기록한다.

## 캐릭터 일관성

- 외형 앵커는 `characters.md`의 `Appearance`에서 가져온다. 이미지 자산 파일에서 따로 새로 쓰면 두 문서가 갈라지고, 갈라진 사실은 반드시 나중에 충돌한다.
- **베이스의 첫 두세 태그가 그 인물의 식별 포인트여야 한다.** 뒤쪽 태그는 가중치가 낮아 묻히고, 썸네일 크기에서는 미묘한 차이가 전부 사라진다. 베이스 목록을 위에서 아래로 훑었을 때 앞부분만 읽어도 서로 다른 인물임이 드러나지 않으면, 생성된 이미지도 서로 닮는다.
- 인물 수만큼 베이스를 다 쓴 뒤 **명부 단위로 한 번 검토한다.** 개별로 보면 다 그럴듯한데 나란히 놓으면 절반이 같은 사람인 경우가 흔하다.
- 인물별 시드를 고정하면 같은 인물의 상황 변형끼리 닮는다. 시드는 자산 파일에 기록한다.
- 그래도 조합 생성만으로는 동일 인물성이 완전히 유지되지 않는다. 정확한 재현이 필요하면 로라 학습을 전제하고, 학습용 데이터셋 축을 별도로 둔다.

로라 학습용 데이터셋을 생성 이미지로 만들 때:

- 변형 축(구도·조명·표정·의상)을 **넓게** 벌린다. 서로 닮은 12장은 과적합을 보장한다.
- 에포크마다 저장한다. **최고 성능 체크포인트는 마지막 에포크가 아니다.** 대개 중간이며, 그 뒤로는 내려간다.
- 같은 시드·같은 프롬프트로 에포크별 비교 격자를 만들어 눈으로 고른다. 이것이 하이퍼파라미터 조정보다 빠르다.

## 배치 생성 도구 규약

자산이 수십 장을 넘으면 도구를 만든다. 다음을 지킨다.

- **설정과 코드를 분리한다.** 체크포인트·로라·스텝·CFG·샘플러·프리셋은 전부 설정 파일에 둔다.
- **백엔드를 추상화한다.** 같은 프롬프트 자산이 여러 실행기에서 돌아야 한다. 특히 로라 전달 방식이 다르다.

| 백엔드 | 로라 전달 | 체크포인트 지정 |
|---|---|---|
| A1111 / Forge | 프롬프트에 `<lora:이름:가중치>` 삽입 | `override_settings.sd_model_checkpoint` |
| ComfyUI | `LoraLoader` 노드 체인 | 체크포인트 로더 노드 |

- **출력 경로가 프롬프트의 URL 패턴과 같은 축으로 떨어지게 한다.** 규칙이 `{BASE}/인물/상황.png`면 출력도 `out/인물/상황.png`여야 한다. 업로드가 단순 복사가 되어야 사람이 실수하지 않는다.
- 최소 CLI: 실제 설치된 모델 목록 조회, 자산 존재 확인, 생성 없이 프롬프트만 출력, 대상 한정, 기존 파일 건너뛰기와 강제 재생성.

## API 코드는 목 서버로 검증한다

GPU 없이 실행할 수 없는 코드를 검증 없이 인계하지 않는다. 실행기 API를 흉내내는 목 서버를 함께 만든다.

**목 서버가 성공만 흉내내면 쓸모가 없다.** 실제 서버처럼 없는 모델·없는 로라·없는 샘플러에 400과 404를 돌려줘야 한다. 이 조건을 지킨 목이 실제로 잡아낸 결함:

- 생성 없이 확인만 하는 옵션이 특정 조합에서 실제로 파일을 생성했다. 분기 순서 문제였고, 목 없이는 발견되지 않았다.
- 자산 확인은 통과하는데 생성이 404로 실패했다. 실행기가 체크포인트를 `파일명.safetensors [해시]` 형태의 제목으로 관리하는데 확인 단계와 생성 단계가 서로 다른 문자열을 비교하고 있었다.

목으로 잡히지 않는 것은 실제 하드웨어·드라이버·수치 정밀도다. 그 부분은 검증했다고 보고하지 않고 인계 사항으로 남긴다.

## 환경 문제와 자산 문제를 분리한다

이미지가 안 나올 때 프롬프트부터 의심하면 시간을 크게 버린다. 먼저 범위를 가른다.

| 증상 | 결론 |
|---|---|
| 모든 모델에서 실패 | 환경 문제. 프롬프트·모델은 무관 |
| 특정 모델만 실패 | 모델 계열·설정 불일치 |
| 특정 조합만 실패 | 자산·슬러그 문제 |

범위를 가른 뒤 **최소 재현**으로 좁힌다. 확장 기능·로라·리파이너·업스케일을 전부 끄고 기본 해상도로 한 장을 뽑는다. 여기서 정상이면 하나씩 되돌리며 범인을 찾는다.

실측 사례: 최신 애플 실리콘에서 A1111이 낡은 torch 버전을 고정하고 있어 fp16 연산이 NaN을 뱉었다. 증상은 모든 체크포인트에서 노이즈였고, 모델이나 프롬프트와는 무관했다. 관리가 멈춘 실행기는 신형 하드웨어에서 이런 방식으로 실패한다.

자산 제작 환경 문제는 **작품과 분리된 인계 사항**이다. 스토리챗 빌드 5종은 이미지가 0장이어도 검증을 통과해야 하며, 이미지 생성이 막혔다는 이유로 빌드를 미루지 않는다.

## 금지 패턴

- 축을 닫지 않은 채 프롬프트를 쓰기 시작한다.
- 그림체 문자열을 수십 개 프롬프트에 복사해 넣는다.
- 외형 앵커를 `characters.md`와 이미지 자산 파일에서 따로 관리한다.
- 체크포인트 이름만 보고 품질 프리픽스를 고른다.
- 목 서버 검증 없이 API 코드를 인계한다.
- 이미지가 없으면 응답이 성립하지 않는 출력 규칙을 쓴다.
- 이미지에 핵심 규칙·정사·판정 근거를 싣는다.

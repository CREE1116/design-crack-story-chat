## 전체 흐름

```
story.md ┐
         ├─→ 컴파일 ─→ build/ 5개 ─→ 검증 ─→ 크랙 UI
characters.md ┘
```

**원본은 두 개뿐입니다.** 매니페스트, 상태 파일, 출력 계약 파일, 키워드북 소스 같은 중간 계층을 만들지 않습니다. 사실 하나에 주인이 하나여야 나중에 갈라지지 않습니다.

산출물은 원본에서 매번 다시 생성합니다. `build/` 안의 파일을 직접 고치면 다음 컴파일에 사라집니다.

## 0. 스킬 불러오기

```
design-crack-story-chat 스킬 로딩해줘.
```

에이전트가 `SKILL.md`를 읽고, 작업 종류에 따라 필요한 참조 문서를 골라 읽습니다. 참조 문서가 12개라 전부 읽히지 않으며, 그렇게 설계되어 있습니다.

## 1. 경험 계약 정하기

로어부터 쓰면 반드시 다시 씁니다. 다음 다섯 개를 먼저 확정하세요.

- **전제** — 플레이어가 어떤 상황에 들어가는가
- **플레이어 판타지** — 무엇이 되고 무엇을 하게 되는가
- **핵심 루프** — 관찰 → 결정 → 행동 → 결과 → 새 압력
- **약속** — 이 경험이 끝났을 때 남아야 하는 정서적 변화
- **자유 경계** — 무엇이 authored이고 무엇이 시뮬레이션이며 무엇을 플레이어가 쥐는가

에이전트에게 이렇게 시키면 됩니다.

```
전제는 "게이트가 열린 2047년 서울, 갓 각성한 무소속 헌터"야.
경험 계약부터 잡고 갈등 엔진을 만들어줘. 로어는 아직 쓰지 마.
```

결정을 내리지 않은 채로 컴파일에 들어가지 마세요. 미해결 결정 위에 쌓은 설정은 전부 다시 씁니다.

## 2. 세계 시스템 설계

능력물·생존물·직업물·경쟁물이라면 인물보다 **세계 시스템이 먼저**입니다. 인물의 위치가 시스템으로 표현되기 때문입니다.

네 가지를 정합니다. 전제에 필요 없는 것은 버리세요.

### 등급 체계

인물과 위협에 **같은 척도**를 씁니다. 그래야 둘을 붙여놨을 때 바로 읽힙니다.

> **모든 등급은 최소 하나를 금지해야 합니다.** 강함만 표시하고 아무것도 막지 않는 등급은 장식입니다. 못 들어가는 곳, 못 맞서는 상대, 안 열리는 문 중 하나는 있어야 합니다.

플레이어의 시작 등급도 정합니다. `미측정`도 유효한 상태입니다.

### 위협 분류

반복 등장하는 적대 세력은 **닫힌 목록**이어야 합니다. "몬스터" 하나로는 부족합니다.

유형마다 정할 것: 실루엣 / 행동 / **무엇을 응징하는가** / **무엇이 통하는가** / 등장이 알려주는 정보 / 난도 대역.

- 4~8종. 4종 미만이면 조우가 반복되고, 8종을 넘으면 모델이 구분을 못 합니다.
- **플레이어가 다르게 행동하게 만드는 축**으로 나눕니다. 수·내구·기동·기만·지역 봉쇄 같은 것. 데미지 숫자로 나누면 리스킨입니다.
- `응징`과 `통하는 것`이 없는 유형은 유형이 아닙니다.

### 성장 체계

- 무엇이 자라고 **무엇은 절대 안 자라는지** 적습니다.
- 성장에는 묘사된 인과가 필요합니다. 턴 수나 요청으로는 절대 안 됩니다.
- 가능하면 축을 나눕니다 (총량 대 숙련). 초반 성장이 읽히면서도 등급 균형이 안 깨집니다.
- **상한을 명시합니다.** 금지하지 않은 것은 결국 요청에 의해 주어집니다.

### 경제와 동기

"이 일을 왜 직업으로 하는가"에 답합니다.

- 돈이 되는 일상 업무
- 비상·실패 상황
- **돈이 안 되는 쪽의 비용을 누가 떠안는가**

이게 없으면 모든 세력이 "정의로운 곳"과 "오만한 곳"으로 붕괴합니다. 세력에 취향이 아니라 **입장**을 주는 것이 이 항목입니다.

## 3. 인물 설계

`characters.md` 하나에 전부 씁니다. 인물마다:

| 항목 | 내용 |
|---|---|
| 극적 기능 | 역할·목표·실패 비용·현재 압력 |
| 성격 압축 | MBTI·에니어그램·아키타입 (선택) + 욕구/공포/자아상/모순 |
| **외형** | **필수.** 실루엣·머리·눈·복장·손·자세·습관 동작 |
| 관찰 행동 | 평상/불확실/도전/신뢰↑/경계침해/실패 후 |
| 말투 | 어투·어휘·피할 말버릇 + 감정별 대사 표본 2~5 |
| 지식 | 공개/비공개/오해/초기 미지 |
| 능력 | 효과·발동·비용·한계·실패 |
| 관계 | 대상별 기준 단계·긴장·원하는 변화 |

### 외형: 목표는 아름다움이 아니라 식별

**등장인물 전원이 외형 칸을 채워야 합니다.** 여기가 그 인물의 시각적 단일 출처이고, 이미지 자산을 쓴다면 베이스 프롬프트도 여기서만 파생합니다. 두 곳에서 따로 쓰면 반드시 갈라집니다.

통과 기준은 하나입니다.

> **사진 한 장만 보고 "아, 이 사람"이 즉시 나와야 합니다.**

인물이 늘수록 이게 무너집니다. 개별로 보면 다 그럴듯한데 명부로 늘어놓으면 절반이 같은 사람으로 보입니다.

**인물마다 식별 포인트를 하나씩** 줍니다. 다른 누구도 갖지 않는 시각 특징 하나. 나머지가 비슷해도 이 하나로 구분됩니다. 좋은 포인트는

- **작아져도 살아남습니다** — 실루엣이나 큰 색면에서 드러날 것
- **떼어낼 수 없습니다** — 흉터, 의수, 이질적인 눈, 늘 착용하는 장비. 매번 바뀌는 옷보다 강합니다
- **한 문장에 담깁니다** — "왼팔 전체가 금속". 설명이 길면 포인트가 아닙니다

**능력과 연결되면 최상입니다.** 식별 포인트가 그 인물의 이능이나 이력의 결과이면, 외형이 곧 설정 설명이 됩니다. 보는 것만으로 인물을 알게 되고 텍스트 예산을 따로 쓰지 않습니다.

```
능력의 대가가 몸에 남음  → 계속 쓰면 흰머리가 번지는 인물
능력의 도구가 몸이 됨    → 손끝이 늘 젖어 있는 인물
능력이 실패한 흔적       → 한쪽 눈만 색이 다른 인물
```

억지로 연결하지는 마세요. 자연스럽지 않으면 그냥 구분되는 편이 낫습니다.

**축이 뭉치면 안 됩니다.** 두 인물이 같은 축에서만 다르면 구분되지 않습니다. 머리 색만 다른 두 사람은 흑백이나 썸네일에서 같은 사람입니다. 명부를 표로 만들어 머리·체격·복장 실루엣·액세서리·자세 축마다 값이 몰렸는지 보세요. 같은 조직이라 복장이 통일된다면 다른 축을 더 크게 벌려야 합니다.

변하는 값(현재 감정·부상·위치·의상 변경)은 넣지 않습니다. 그건 상황 모디파이어의 몫입니다.

### 인물이 10명을 넘으면

개별 검토로는 다음이 새어나갑니다. **명부를 표로 뽑아 눈으로 확인하세요.**

- 필수 칸에 빈 곳이 있는가 (성별처럼 당연해 보이는 칸이 실제로 비어 있는 일이 생깁니다)
- 구성 비율 — **손으로 세지 말고 스크립트로 세세요.** 인상은 틀립니다
- 이름이 주는 인상이 설정과 어긋나지 않는가
- 이름·이칭이 서로 구별되는가 (비슷하면 모델이 인물을 혼동합니다)

### 민감 속성

성적 지향, 건강 이력, 트라우마 원인 같은 항목은 배치 경로를 따로 정합니다.

| 위치 | 가능 여부 |
|---|---|
| 캐논 원본 | 가능 (모델에 안 실림) |
| 통합 프롬프트 SAFE | 불가 |
| 통합 프롬프트 UNSAFE | **불가** — 한쪽에만 있으면 변형 쌍이 깨집니다 |
| 키워드북 | 조건부 가능 |
| 플레이어 가시 출력 | 절대 불가 |

속성 자체(`지향=X`)는 어떤 행동도 바꾸지 않습니다. **관찰 가능한 반응과 경계**를 쓰세요.

## 4. 컴파일

```
이제 두 원본에서 5개 산출물 뽑아줘.
```

에이전트가 규칙을 네 경로 중 하나로 배분합니다.

| 규칙 성격 | 가는 곳 |
|---|---|
| 항상 필요 | 통합 프롬프트 양쪽 |
| 도입부 부트스트랩 | 시작 프롬프트 |
| 조건부 상세 | 키워드북 |
| 플레이어가 반복 호출 | 크랙 숏컷 |

각 규칙은 **정확히 한 곳에만** 갑니다. 중복은 글자 예산을 먹고 충돌을 만듭니다.

### 글자수는 토큰이 아닙니다

크랙 상한은 **글자수**를 셉니다. 토큰 절약 습관이 여기서는 정반대로 작동합니다.

> 한국어 규칙문을 영어로 옮기면 글자수가 **약 두 배**가 됩니다. 통과하던 프롬프트가 그것만으로 상한을 넘습니다.

- 한국어 작품이면 규칙문도 한국어로 씁니다. 영어로 "최적화"하지 마세요.
- 짧고 안정된 ASCII 식별자(ID·슬러그·기호 이름)는 영어로 둡니다.
- **프롬프트가 넘치면 번역은 절대 해법이 아닙니다.** 범위를 줄이세요.

산출물별 상한은 [artifacts.md](artifacts.md)를 보세요.

### 자리가 모자라면 정형화부터

산문으로 쓴 프롬프트는 줄일 데가 없어 보이지만 **어미와 연결어가 10% 이상을 먹고 있습니다.** 문서 전체를 정형 문법으로 옮기면 규칙을 하나도 잃지 않고 그만큼이 빠집니다.

반복되는 어미를 기호로 승격하는 것부터 합니다. 부정형이 거의 항상 1순위입니다.

| 승격 | 원래 | 회당 절감 |
|---|---|---|
| `×` | `~하지 않는다` | 5~7자 |
| `≠` | `~는 ~를 뜻하지 않는다` | 8자 이상 |
| `=` | `~는 ~이다` | 3~6자 |
| `→` | `~하면 ~한다` | 3~5자 |

기호 하나를 범례에 추가하는 비용이 10~15자이므로 **네 번 이상 회수되면 이득**입니다. 도입 전에 원문에서 세어보세요.

**압축 강도는 내용에 따라 다르게 줍니다. 이게 유일한 안전장치입니다.**

- 세계 설정, 배경, 절차 서술, 형식 규칙 → 세게
- 플레이어 주도권, 동의, 금지 경계 → **약하게**

주도권과 동의 규칙은 모델이 애매할 때 돌아갈 자리입니다. 몇 글자 아끼자고 해석 여지를 만들지 마세요. `잠긴 행동은 제안·암시·완료하지 않는다`는 `잠긴 행동×`보다 길지만 그대로 둡니다.

**그리고 반드시 손실을 기계로 검증하세요.** 압축은 손실이 조용히 일어나는 작업이라 읽어봐서는 못 찾습니다. 원본의 규칙을 하나씩 지문(그 규칙에만 나오는 단어들)으로 적고 압축본에서 살아있는지 확인합니다.

예제 프로젝트는 이 방식으로 6,921 → 6,553자가 됐고, 규칙 55개 전부 보존됐습니다. 확보한 여백에는 그동안 자리가 없어 못 넣던 경제 구조·성장 체계·길드장 명부가 들어갔습니다. 다만 **줄인 만큼을 전부 다시 채우지는 않습니다.** 압축의 목적은 여백을 만드는 것입니다.

## 5. 검증

```bash
./scripts/validate.sh <내_프로젝트>
```

여섯 개 스크립트가 돕니다. 자세한 것은 [validation.md](validation.md).

특히 **3슬롯 시뮬레이션**은 반드시 돌리세요. 항목을 하나씩 검토해서는 충돌을 절대 못 찾습니다. `.assets/kb-scenes.txt`에 실제로 나올 법한 장면을 나열해야 보입니다.

```
등록층 대기: 협회 본부 등록층에서 번호표를 들고 측정 순서를 기다린다
길드 부스 순회: 발할라 아발론 에덴 바벨 네 길드의 부스를 둘러본다
```

슬롯 초과가 나오면 셋 중 하나로 대응합니다.

1. **등록 순서를 바꿔** 밀리는 항목이 서로 다른 진영·주제에 흩어지게 함
2. 키워드를 좁힘
3. 항목을 합침

그리고 **밀려도 안전한지** 확인하세요. 밀린 항목의 이름이 통합 프롬프트에 한 줄이라도 씨앗으로 있으면 안전하고, 없으면 모델이 지어냅니다.

## 6. 크랙에 등록

| 산출물 | 넣는 곳 |
|---|---|
| `integrated-prompt-safe.md` | 통합 프롬프트 (SAFE) |
| `integrated-prompt-unsafe.md` | 통합 프롬프트 (UNSAFE) |
| `prologue.md` | 프롤로그 |
| `start-prompt.md` | 시작 프롬프트 |
| `keyword-book.md` | **항목별로 하나씩 수동 등록** |

키워드북만 붙여넣기가 안 됩니다. 파일 안의 각 `# kb.*` 블록이 UI의 항목 하나에 대응하며, `activation_setting`·`activation_when`·`keywords`·본문을 각각 넣습니다.

> **등록 순서가 산출물의 일부입니다.** 파일에 적힌 순서대로 등록하세요. 나중에 순서를 바꾸면 3슬롯 경합 결과가 달라집니다. 순서를 바꿨다면 어떤 항목을 다시 등록해야 하는지 기록해두세요.

## 7. 플레이하며 고치기

실제로 플레이하면 문서로는 안 보이던 것이 나옵니다. 자주 나오는 것들:

- 상태창이 아예 안 뜬다
- 메타 발언이 샌다 (`(선택사항, OOC)` 같은 것이 세계 안 문서에 찍힘)
- 상태창과 본문이 서로 모순된다
- 의미 없는 이모지가 나온다

전부 원인과 대처가 정리되어 있습니다. [troubleshooting.md](troubleshooting.md)를 보세요.

고칠 때는 **`build/`를 직접 고치지 말고 원본을 고친 뒤 다시 컴파일**합니다. 빌드 파일을 제2의 원본으로 만들면 그때부터 갈라지기 시작합니다.

### 원본을 고쳤을 때

`story.md`나 `characters.md`를 수정하면 산출물이 낡습니다. **문제는 이 상태가 아무 신호도 내지 않는다는 것입니다.** 빌드는 여전히 모든 검사를 통과하고, 크랙에 올라간 프롬프트만 조용히 옛날 인물을 연기합니다.

```bash
python3 skills/design-crack-story-chat/scripts/check_freshness.py <내_프로젝트>
```

컴파일 시점의 원본 지문을 섹션 단위로 기록해뒀다가 비교합니다. 무엇이 바뀌었는지, 그래서 **어느 산출물을 다시 봐야 하는지**까지 알려줍니다.

```
STALE characters.md: 수정 1 · 추가 0 · 삭제 0
  ~ char.ban-hosik — 반호식 「不壊」 · 발할라 길드장
      → 통합본 현장 인물 씨앗 · 해당 키워드북 항목 · 이미지 프롬프트
```

바뀐 섹션 제목으로 영향 범위를 추정합니다.

| 바뀐 곳 | 다시 볼 산출물 |
|---|---|
| 인물의 Appearance | 이미지 프롬프트 |
| 인물 섹션 전반 | 통합본 씨앗 · 해당 키워드북 항목 · 이미지 프롬프트 |
| 세계 법칙·등급·위협·성장·경제 | 통합본 세계 법칙 · 관련 키워드북 |
| 프롤로그·오프닝 | `prologue.md` · `start-prompt.md` |
| 관계·이벤트·아크 | 통합본 진행·관계 |

재컴파일한 뒤에는 기준을 갱신합니다. **이게 컴파일의 마지막 단계입니다.**

```bash
python3 .../check_freshness.py <내_프로젝트> --stamp
```

`validate.sh`가 이 검사를 맨 앞에 돌리므로, 검증만 돌려도 낡은 상태는 바로 걸립니다.

## 작업 규칙

스킬이 강제하는 것들입니다. 어기면 나중에 반드시 비용을 냅니다.

- **원본은 두 개.** 중간 계층을 만들지 않습니다.
- **사실 하나에 주인 하나.** 같은 사실이 두 파일에 있으면 갈라집니다.
- **7,000자는 천장이지 목표가 아닙니다.** 여백을 남기세요. 채우려고 로어를 넣지 마세요.
- **SAFE/UNSAFE는 표현 강도만 다릅니다.** 한 번에 같이 생성하고, 따로 관리하지 않습니다.
- **플레이어의 대사·생각·동의·결정을 대신 쓰지 않습니다.**
- **확인되지 않은 플랫폼 동작을 추측해 규칙으로 만들지 않습니다.** 모르면 모른다고 표시합니다.
- **검사기를 믿기 전에 실패해야 할 입력을 먹여보세요.** 모든 것을 통과시키는 검사기는 탐색을 끝내버립니다.
